# Architecture

Software architecture of `spring-bpmn`, a BPMN 2.0 process engine for Spring Boot. Read this in every session before changing module structure. Update it whenever modules, dependency directions or key types change. Build/style rules are in `AGENTS.md`.

## Goal

`spring-bpmn` reads and interprets BPMN 2.0 files and executes the processes. It delegates scheduling/execution of work to `spring-tasks` and storage of models and history through its repository API (`de.nemeses.spring.bpmn.repository`).

## Modules and dependency directions

```text
spring-bpmn ──> spring-tasks   <── spring-tasks-jpa
     ^                         <── spring-tasks-jms
     └─────── spring-bpmn-repository-jpa
```

An arrow points from the dependent module to the module it depends on. Implementation modules depend on their API module, never the other way round. `spring-bpmn` depends only on the API module `spring-tasks` and contains the repository API itself; concrete backends are chosen by the application by adding the implementation module to its classpath.

| Module | Responsibility | State |
|--------|----------------|-------|
| `conventions` | Checkstyle/PMD/SpotBugs rulesets and Eclipse prefs. Independent POM. | done |
| `spring-tasks` | Interface to schedule and execute tasks: `TaskService`, `TaskImplementation`, `TaskPersistence` (`TaskInfo`). | schedule and execute (worker pool in `TaskService`) |
| `spring-tasks-jpa` | Stores tasks in JPA (`JpaTaskPersistence`, `TaskEntity`, table `spring_tasks`) and hands due tasks to the `TaskService` workers via `next()`. | persist and next (polling) implemented, untested |
| `spring-tasks-jms` | Sends scheduled tasks to a JMS queue and listens to it for execution. | `JmsTaskPersistence` (send, blocking `next()`, ack/recover); tests use embedded Artemis |
| `spring-bpmn-repository-jpa` | Only repository implementation for now (implements the API in `spring-bpmn`); stores everything in JPA. | `ProcessDefinitionService`, `ProcessInstanceRepository` (with pessimistic `lock`) and `ProcessStepRepository` implemented and tested (H2) |
| `spring-bpmn` | Reads and interprets BPMN files; uses `spring-tasks` to run steps; contains the repository API (`ProcessDefinitionService`) for models/history. | Generated JAXB model (BPMN 2.0 XSDs, one package per namespace: `de.nemeses.spring.bpmn.model.bpmn20` (BPMN20 + Semantic), `.bpmndi`, `.dc`, `.di`; classes without the `t` prefix, see `src/main/xjb/bpmn.xjb`); `BpmnParser` (JAXB unmarshalling of BPMN documents into the model, `BpmnParseException`); `ProcessEngineService` starts process instances and schedules their start events as `bpmnNodeTask` tasks; `BpmnNodeExecutor` executes one process step per `bpmnNodeTask`: `startEvent`, `endEvent`, `task`, `serviceTask`, `exclusiveGateway` and `parallelGateway` (fork and join) nodes, evaluating sequence flow conditions as SpEL (`ConditionEvaluator`) (no event definitions); `task` and `serviceTask` with `standardLoopCharacteristics` (`ActivityLoop`, all iterations in one step; no multi-instance yet); service tasks can change process variables, stored in the node's transaction |

## Key types

- `de.nemeses.spring.tasks`: `TaskService` (public entry: `trigger`, `schedule`; a `SmartLifecycle` that starts `spring.tasks.pool-size` worker threads on context start and interrupts/awaits them on stop), `TaskProperties` (`@ConfigurationProperties` record for all `spring.tasks.*` settings of `TaskService`, enabled by `TaskConfiguration`), `TaskImplementation<T>` / `JsonPayloadTaskImplementation<T>` (Jackson), `TaskPersistence` + `TaskInfo` (`next()`, `complete()`, `fail(Exception)`), `TaskException`, `PayloadException`, `TaskConfiguration`.
- `de.nemeses.spring.tasks.jpa` (module `spring-tasks-jpa`): `JpaTaskPersistenceAutoConfiguration`, `JpaTaskPersistence`, `TaskEntity`.
- `de.nemeses.spring.tasks.jms` (module `spring-tasks-jms`): `JmsTaskPersistenceAutoConfiguration` (registers `JmsTaskPersistence`), `JmsTaskProperties` (`spring.tasks.jms.queue`, default `spring.tasks`), `JmsTaskPersistence`: `persist` sends a text message with `beanName` property and JMS 2.0 delivery delay for `earliestExecution`; `next()` receives with client acknowledge; `complete()` acknowledges, `fail()` recovers (redelivery).
- `de.nemeses.spring.bpmn` (module `spring-bpmn`): `BpmnParser` (`parse(InputStream)` returns `Definitions`), `BpmnParseException`, `ProcessDefinitionSource` (`Collection<Resource> resources() throws IOException`; beans of this type contribute BPMN documents), `ConfiguredLocationsProcessDefinitionSource` (the default source; resolves, de-duplicated, the location patterns from `spring.bpmn.process-definition-locations`, injected with `@Value`), `ProcessDefinitionRegistrar` (an `ApplicationRunner`), `ProcessDefinitionAutoConfiguration` (component-scans the package, all classes are `@Component`s wired by constructor; requires a `ProcessDefinitionService` bean, e.g. from `spring-bpmn-repository-jpa`). The registrar iterates all `ProcessDefinitionSource` beans, parses each document and registers every `process` separately (name = `name` attribute, else `id`; the whole document is stored as XML). A process is skipped if the latest registered version has the same MD5 hash (`ProcessDefinition.md5Hash()`, default method over `bpmnXml()`). Parse/read errors abort startup.
  `ProcessEngineService` (`@Transactional`): `startProcess(String name, Map variables)` retrieves the latest definition and forwards to `startProcess(ProcessDefinition, Map variables)`, which finds the BPMN `process` whose name (else id) equals the definition name, creates a `ProcessInstance` through the `ProcessInstanceRepository` and creates one `ProcessStep` (through the `ProcessStepRepository`) and triggers one `bpmnNodeTask` per `startEvent` of that process via `TaskService`. Failures (unknown definition, parse error, no matching process, no start event) throw the checked `ProcessEngineException` and roll back. `BpmnNodeTask` (bean `bpmnNodeTask`, `JsonPayloadTaskImplementation<UUID>`; the payload is the id of the `ProcessStep` to execute) calls `BpmnNodeExecutor.executeNode(UUID stepId)` (resolved through an `ObjectProvider`, because the executor depends on the `TaskService`, which depends on all task implementations); a `ProcessEngineException` becomes a `TaskException`, so the task fails and the backend redelivers it.
  `BpmnNodeExecutor` (`@Transactional`): retrieves the step, locks its instance (`ProcessInstanceRepository.lock`, pessimistic write lock, so the steps of one instance run one after the other), then reads the pending steps at the step's node. It skips the step if it is no longer pending (a task delivered again, or a join step already completed by another step) or if the instance has ended. Otherwise it parses the definition and selects the process like `ProcessEngineService` (flow node and sequence flow lookups in `ProcessNavigator`), runs the node, completes the step (sets its `endDate`) and, for each sequence flow taken, creates a step for the target node (with the flow as `incomingFlowId`) and triggers a `bpmnNodeTask` with its id, all in one transaction. Node types: `startEvent`, plain `task` (nothing to do) and `parallelGateway` with at most one incoming flow (fork) take all outgoing flows; a `parallelGateway` with more incoming flows is a join: it continues only if a step is pending at the gateway for every incoming flow, then completes the oldest pending step of each incoming flow and takes all outgoing flows once; otherwise the step stays pending (parked at the join: a step without `endDate` whose node is the join; steps have no state); `serviceTask` calls the `BpmnNodeImplementation` bean named by the extension attribute `bean` in namespace `https://nemeses.de/spring-bpmn` (`BpmnNodeExecutor.BEAN_ATTRIBUTE`, read from the JAXB `otherAttributes`, e.g. `spring:bean="checkOrder"`), stores the variables it changed (`updateVariables`, only if something changed), then takes its outgoing flows like a plain `task`, evaluating their conditions against the variables as changed by the task: activities take every outgoing flow without condition plus every flow whose condition is true, and their `default` flow only if no condition is true; `exclusiveGateway` takes the first non-default outgoing flow in document order that has no condition or whose condition is true, else its `default` flow, and fails if there is none; `endEvent` without event definition completes its step and sets the instance's end date (`updateEndDate`) only if no step of the instance is pending any more (`ProcessStepRepository.countPending`). Flow selection lives in the package-private `FlowSelector`, the service task call and variable storage in the package-private `ServiceTaskInvoker`; flows out of `startEvent` and `parallelGateway` (fork and join) must not have a `conditionExpression` (fails otherwise). `task` and `serviceTask` may have `standardLoopCharacteristics`, run by the package-private `ActivityLoop` (through `ServiceTaskInvoker`): all iterations run within the one step (one transaction, the loop counter is not stored, no step per iteration), then the outgoing flows are selected once against the variables after the last iteration. An iteration runs while `loopCounter` (iterations completed so far, starting at 0) is less than `loopMaximum` (if given; `loopMaximum="0"` runs none) and the `loopCondition` is true; with `testBefore="false"` (default) the condition is not checked before the first iteration (do-while), with `testBefore="true"` it is (while, possibly zero iterations). The `loopCondition` is evaluated by `ConditionEvaluator` against the variables as changed by the previous iterations plus the variable `loopCounter` (hiding a process variable of that name; not stored). Without `loopCondition` the activity runs `loopMaximum` times; without both, or with a negative `loopMaximum`, it fails. Each service task iteration gets a new `BpmnNodeContext` seeing the changes of the previous iterations, and `BpmnNodeContext.loopCounter()`; the variables are stored once after the last iteration; a failing iteration discards all of them. Every other node type, and any activity with `multiInstanceLoopCharacteristics`, fails with `ProcessEngineException`.
  `ConditionEvaluator` (`@Component`) evaluates a `conditionExpression` (and, through `evaluate(String description, Expression, String, Map)`, any boolean expression such as a `loopCondition`) as Spring SpEL against the process variables. Language: the `language` of a `formalExpression`, else the `expressionLanguage` of `definitions`; accepted are `ConditionEvaluator.SPEL_LANGUAGE` (`https://nemeses.de/spring-bpmn/spel`) and the BPMN default `http://www.w3.org/1999/XPath` (which JAXB reports when the attribute is absent, so it cannot be told from an explicit XPath declaration and is evaluated as SpEL); any other language fails. Plain `tExpression` conditions are evaluated the same way. The text may be wrapped in `${...}`. Variables are readable by name (`amount > 5`, root object is the variable map), as `#amount` and via `['amount']`; nested values through map keys or getters. The context is a read-only `SimpleEvaluationContext` (no assignment, type references, constructors, bean references or method calls). Unknown variables, syntax errors and non-`Boolean` results fail with `ProcessEngineException`.
  `BpmnNodeImplementation` (`execute(BpmnNodeContext) throws ProcessEngineException`): code bound to a `serviceTask`. `BpmnNodeContext` gives `processInstanceId()`, `nodeId()`, `loopCounter()` (iterations of a standard loop completed before this one, else 0), `variables()` (unmodifiable, includes the node's own changes) and `setVariable(String, Object)` (no `null`s) / `removeVariable(String)`. The context starts from the variables read after the instance was locked; the changes are collected in it (package-private `NodeContext`) and written with `ProcessInstanceRepository.updateVariables` after the implementation returns, in the node's transaction and before the step is completed, the outgoing flow conditions are evaluated and the follow-up steps and `bpmnNodeTask`s are created; if the implementation fails, they are discarded. Because of the instance lock, steps of parallel paths of one instance read and write the variables one after the other (whole-map replace, no lost updates). The auto-configuration therefore also needs a `ProcessInstanceRepository`, a `ProcessStepRepository` and a `TaskService` bean (the latter e.g. via `TaskConfiguration` plus a `TaskPersistence`).
- `de.nemeses.spring.bpmn.repository` (module `spring-bpmn`): `ProcessDefinition`, `NoSuchProcessDefinitionException`, `ProcessDefinitionService` (`register`, `retrieveLatest`, `retrieveAll`), `ProcessInstance` (`id` (`java.util.UUID`), `processDefinition` (the exact version started from), `variables`, `startDate`, `endDate` (`null` while running)), `ProcessInstanceRepository` (`create(ProcessDefinition, Map)` assigns id and start date; `retrieve(UUID)`, `lock(UUID)` (retrieves and locks the instance exclusively until the transaction ends; must run in a transaction), `updateEndDate(UUID, Date)` and `updateVariables(UUID, Map)` (replaces all variables) throw the checked `NoSuchProcessInstanceException` if unknown), `ProcessStep` (one execution of a flow node: `id`, `processInstanceId`, `nodeId`, `incomingFlowId` (`null` for start events), `startDate`, `endDate` (`null` while pending); no state, pending means no `endDate`; steps are never deleted, so they are also the trail of an instance's activity), `ProcessStepRepository` (`create(instanceId, nodeId, incomingFlowId)` assigns id and start date, throws `NoSuchProcessInstanceException`; `retrieve(UUID)` and `complete(Collection<UUID>, Date)` throw `NoSuchProcessStepException`; `pending(instanceId, nodeId)` (oldest first) and `countPending(instanceId)` read the current stored state; `steps(instanceId)` returns the trail ordered by start date).
- `de.nemeses.spring.bpmn.repository.jpa` (module `spring-bpmn-repository-jpa`): `JpaBpmnRepositoryAutoConfiguration` (registers `JpaProcessDefinitionService` and imports the `@Component` `JpaProcessInstanceRepository`, conditional on `EntityManagerFactory`, adds the package to the entity scan), `JpaProcessDefinitionService` (every `register` adds a version; latest = newest `createdDate`; `retrieveLatest` throws the checked `NoSuchProcessDefinitionException` if unknown; `createdDate` defaults to the first-persist time via `@PrePersist`), `ProcessDefinitionEntity` (table `spring_bpmn_process_definition`; unique index on `process_definition_name` + `created_date`, so two versions of one name cannot share a creation date; `UUID` id generated on persist), `JpaProcessInstanceRepository` (`@Component`, `@ConditionalOnMissingBean(ProcessInstanceRepository)`, constructor-injected shared `EntityManager`, `@Transactional`; only accepts definitions stored by `JpaProcessDefinitionService`; `lock` refreshes the instance with `LockModeType.PESSIMISTIC_WRITE` (`SELECT ... FOR UPDATE`) and requires a running transaction (`Propagation.MANDATORY`)), `JpaProcessStepRepository` (`@Component`, `@ConditionalOnMissingBean(ProcessStepRepository)`, also imported by the auto-configuration; pending steps are queried from the database), `ProcessStepEntity` (table `spring_bpmn_process_step`: `id` (UUID), `process_instance_id` (FK to `spring_bpmn_process_instance`), `node_id`, `incoming_flow_id` (nullable), `start_date`, `end_date` (nullable); indexes on `process_instance_id, end_date` and `process_instance_id, node_id, end_date`), `ProcessInstanceEntity` (table `spring_bpmn_process_instance`, `UUID` id, many-to-one `process_definition_id` to `ProcessDefinitionEntity`, variables stored as JSON by `VariablesConverter`).

## Flow of a task

1. Caller invokes `TaskService.trigger(beanName, payload)` or `schedule(beanName, payload, earliestExecution)`.
2. `TaskService` looks up the `TaskImplementation` by Spring bean name and serializes the payload.
3. The active `TaskPersistence` (JPA or JMS) stores or sends it.
4. Each `TaskService` worker thread loops: `TaskPersistence.next()` (blocks until a task is due), looks up the `TaskImplementation` by bean name, deserializes the payload and calls `execute` (`TaskImplementation.executeSerialized`), then reports `TaskInfo.complete()` on success or `TaskInfo.fail(e)` on any exception (including an unknown bean name or a payload error). If `next()` itself throws a runtime exception the worker logs it and retries after 1 s. On context stop the workers are interrupted and awaited (up to 30 s).

## Extension points

- New task type: Spring bean implementing `TaskImplementation`; referenced by bean name.
- New task backend: new module `spring-tasks-<name>` depending on `spring-tasks`, providing a `TaskPersistence` bean via auto-configuration (`@ConditionalOnMissingBean(TaskPersistence.class)`), registered in the module's own `AutoConfiguration.imports`.
- New repository backend: new module `spring-bpmn-repository-<name>` implementing the repository interfaces the same way.
- Engine logic belongs in `spring-bpmn`, built on `TaskService`; do not add a second scheduler.

## Packaging conventions

Implementation modules keep the package names of their API (`...tasks.jpa`, `...tasks.jms`) so consumers are not affected by the module split. Every package needs `package-info.java`; auto-configurations are registered in the `AutoConfiguration.imports` file of the module that contains them.

## Configuration properties

Complete list of all configuration properties. Keep this table up to date when adding or changing properties.

| Property | Module | Default | Description |
|----------|--------|---------|-------------|
| `spring.tasks.pool-size` | `spring-tasks` | `10` | Number of worker threads `TaskService` starts to execute tasks. `0` starts no worker (tasks are only scheduled, not executed); negative values are rejected (`TaskProperties`). |
| `spring.tasks.error-backoff` | `spring-tasks` | `1s` | `Duration` a worker pauses after `TaskPersistence.next()` failed, to avoid a busy loop (`TaskProperties`). |
| `spring.tasks.shutdown-timeout` | `spring-tasks` | `30s` | Maximum `Duration` `TaskService` waits for the interrupted workers to terminate when the context stops (`TaskProperties`). |
| `spring.tasks.jms.queue` | `spring-tasks-jms` | `spring.tasks` | Name of the JMS queue tasks are sent to and received from (`JmsTaskProperties`). |
| `spring.tasks.jpa.max-results` | `spring-tasks-jpa` | `20` | Maximum number of due tasks fetched per database query. Fetched tasks are claimed (`RUNNING`) and served from an in-memory list; the database is queried again only when that list is empty. |
| `spring.bpmn.process-definition-locations` | `spring-bpmn` | `classpath*:/process-definitions/*.bpmn` | Resource patterns scanned on startup for BPMN documents to register as process definitions (`ConfiguredLocationsProcessDefinitionSource`). |
